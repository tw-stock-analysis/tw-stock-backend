# 開發順序、驗收與部署

以下是待實作工作，不是已完成進度。不預估缺乏依據的完成天數；每階段都有可驗收成果。

## 1. 分階段交付

| 階段 | 具體交付 | 完成條件 |
| --- | --- | --- |
| P0 資料與契約 | 代表性上市／上櫃標的，驗證日價量、營收、財報；固定 API 與缺值語意 | 記錄來源、條款、時間、單位、歷史覆蓋；不支持的範圍縮小；未確認不進入該資料功能實作 |
| P1 工程骨架 | React/TS/Vite、FastAPI、開發 PostgreSQL、依賴鎖定、健康檢查、CI | 乾淨 clone 可啟動；前端可呼叫後端；測試不依賴正式憑證 |
| P2 個股完整流程 | 主檔、日資料同步、搜尋、個股摘要、K 線、量能 | 真實資料抽樣可比對；無成交、缺漏與上游故障正確；URL 重整可還原 |
| P3 會員與自選股 | sessions、CSRF、註冊登入、信箱驗證、重設密碼、清單與設定 | A 無法讀寫 B；登出撤銷；跨頁重整維持登入；重複新增／多頁修改結果一致 |
| P4 基本面 | 月營收、可驗證 EPS／估值／財報比率 | 公告日、累計／單季、合併／個別、單位正確；負值／缺值／產業適用性通過 |
| P5 技術指標 | MA、RSI、MACD、布林；圖表控制與替代表格 | 固定樣本逐值比對；暖機、停牌、缺口與視窗切換行為一致 |
| P6 上線準備 | HTTPS、正式信件、排程、備份、監測、發版 | staging E2E、備份還原、部署復原與手機流程通過 |

P2 可先用有標記的固定 fixture 建 UI，但階段完成必須驗證真正資料接入。P0 是技術與來源可行性驗證，不能只因端點存在就當作歷史資料與公開展示條件都完成。

## 2. 每個功能的寫法

一次完成一條使用流程，例如「登入使用者把股票加入自選」：固定 API → migration 與交易 → 後端測試 → 產生前端型別 → UI 串接 → E2E 驗證。每個 PR 說明行為、驗收、資料庫變更及未涵蓋項目。

只在功能需要時新增表與模組。資料接入與會員模組可在契約固定後分開開發；不要一次產生所有功能再到最後整合。

## 3. 必要測試

| 層 | 重點 |
| --- | --- |
| 純計算 | 指標固定序列、零漲跌、暖機、除零、EPS 口徑 |
| Parser | 民國日期、千元／元／股／張、缺值字串、欄位消失、上游 HTML 錯誤頁 |
| PostgreSQL | migration 建空庫／升版、FK／唯一約束、並行新增、rollback、到期 session |
| API | 授權、CSRF、reset token 重播、版本衝突、資料範圍及參數限制 |
| 前端 | 搜尋鍵盤操作、狀態呈現、數值格式、URL、舊請求取消、帳號切換 |
| E2E | 搜尋→個股→登入→自選→重整→移除→登出；信箱驗證／重設；手機操作 |
| 運維 | 上游中斷、重跑 job、程序中止恢復、備份還原 |

整合測試用真正 PostgreSQL，不用 SQLite 模擬 asyncpg 與鎖。CI 使用隔離的 PostgreSQL service；市場 API 以可追溯 fixture 測試，provider smoke test 另外執行。[GitHub PostgreSQL service 文件](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers)。

## 4. 效能與可用性目標

以下是待測量的驗收目標：在記錄好的硬體／資料量環境，以 20 個並行使用者測試；熱資料搜尋與會員 API p95 <300ms，兩年日 K＋指標 p95 <800ms，皆不包含外部資料擷取。

- 圖表程式延後載入，固定容器高度避免版面跳動；以固定手機模擬環境建立效能基線。
- 一次歷史查詢最多兩年、1,500 根；超出回 422，不默默截短。
- 外部來源故障時仍顯示上個有效批次及過期狀態，會員功能獨立可用。
- 新資料批次發布後，讀取端五分鐘內應能看見新版本；不以抓取時間冒充交易日期。
- 效能不達標先檢查查詢、索引、回傳大小與程序分工，再評估 Redis／PgBouncer／工作佇列。

## 5. 開發與部署環境

| 環境 | 預設 |
| --- | --- |
| WSL 本機 | 專案在 Linux 檔案系統；Node/Python 皆於 WSL；React/FastAPI 熱更新；PostgreSQL 可用 Compose |
| CI | Linux runner、鎖定依賴、臨時 DB、fixtures、無正式憑證 |
| staging | 與正式相同的啟動／migration 流程，獨立 DB 與信件設定 |
| production | 同源 HTTPS、前端靜態服務、FastAPI、獨立同步程序、PostgreSQL |

供應商尚未選定。初期使用一個 API instance、一個同步程序即可；增加 API processes 時必須重算連線池總額。migration 是部署前執行一次的工作。[FastAPI 部署文件](https://fastapi.tiangolo.com/deployment/concepts/)。

## 6. 發版、備份與觀測

1. 建置與測試通過，檢查 OpenAPI 型別及 migration。
2. staging migration、代表性同步與完整 E2E 通過。
3. 資料庫先採向後相容的新增與回填；新舊程式可共存後再移除舊欄位。
4. 正式 migration 只跑一次，成功後切換應用程式；失敗停止切換。
5. 每日備份使用者資料；初期目標 RPO 24 小時、RTO 4 小時，以還原演練確認，需求增加再加 PITR。
6. 市場資料即使可重抓，也需保存版本及來源證據；歷史修訂不一定能從上游重新取得。

監測 request_id、API 延遲、DB pool 等待、同步失敗、最新交易日及備份結果。日誌不包含密碼、Cookie、CSRF／reset token 或完整私人請求。開發用信件捕捉器可供驗證流程，公開註冊前必須接上實際寄信服務。
